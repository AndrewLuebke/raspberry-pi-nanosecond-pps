The 13 ns Pi 4

How one evening took a Raspberry Pi 4 stratum-1 from 337 ns to 13.4 ns of per-pulse PPS timestamp jitter — by moving one interrupt, isolating one core, and firing a decoy interrupt 150 µs before every real one.

1 · The three questions, answered

Can the GPIO IRQ be moved off its default core? Yes — proven live three ways. July's "dead end" was a userspace-visibility artifact: chained parent IRQs are allocated after init_irq_proc()'s one-shot sweep and never pass request_irq(), so no /proc/irq/N directory can ever exist for them — but underneath, the GPIO bank-0 parent (GIC SPI 113, virq 23) is an ordinary GICv2 SPI. A one-byte GICD_ITARGETSR poke retargets it (verified with a 5-second live test), a 40-line GPL module calling irq_set_affinity() does it properly (deployed), and one line in the pinctrl probe will do it permanently at the next kernel build. The irqaffinity= boot param can not do it: the boot CPU is force-added to the mask and GICv2 picks the lowest CPU — always CPU0.

What can Linux still do, short of external hardware? Far more than the July verdict ("on-Pi software route EXHAUSTED") allowed. Steering to an isolated core erased the multi-microsecond tails; a self-injected warm-up interrupt erased the remaining core scatter. Together: 25×.

Where is the silicon limit? σ ≈ 10–20 ns — GPIO synchronizer (~1 ns), GIC-400 prioritization (2–12 ns), A72 exception entry (3–10 ns), and the 54 MHz counter's 18.5 ns quantization (σ 5.3 ns). Tonight's 13.4 ns is at that floor. The interrupt path is no longer this box's bottleneck.

2 · Where the 337 ns actually lived

cache-cold Linux delivery path ≈ 320 ns silicon

The old σ 337 ns budget: almost none of it was hardware.

Three independent research passes (kernel source, ARM GIC-400 TRM + BCM2711 datasheet + published measurements, and bypass-technique prior art) converged on one mechanism: at one pulse per second, the interrupt delivery path — vectors, gic_handle_irq, the IAR read, the irq-domain walk, the pinctrl handler, the clock read — goes cache-cold between every pulse. Each pulse paid ~10–30 DRAM refills and branch mispredicts whose individual timing varies (~130–156 ns per random LPDDR4 read, refresh collisions shaping the tail). That explains the signature finding of the whole program: the jitter was load-invariant, because even a quiet second is enough to randomize the caches.

The clinching evidence: a CoreSight-traced GICv2/ARMv8 study measured the full hardware delivery pipeline at 232 ns latency with a few ns of spread when caches are hot — and 1.5–4.4 µs when cold. Cache state is a ~10× lever on identical silicon. A ~54 ns figure we had seen quoted for a Pi 5 (not verified here) required exactly what we built tonight: an isolated, IRQ-pinned core.

What each lever bought: steering to a merely different busy core bought nothing (and hurt the tails — housekeeping kthreads hold IRQs off longer than CPU0's interrupt traffic). Steering to an isolated core halved σ and crushed the tails — the delivery path stays warm in the core's private L1I passively. The warm shot then covered what isolation can't: the A72's shared, L1D-inclusive L2 lets the other three cores back-invalidate the path's data lines between pulses, so the module re-fetches everything 150 µs before each pulse instead of 1 s. Result: 10× further. A bonus tell: the "constant" 3.28 µs entry→leaf demux delay dropped to 1.80 µs on the isolated core — it was half cache misses all along.

Servo-level, over the same hours: chrony Std Dev 216 ns (Wed) → ~140 (entry-stamp kernel) → 43 (steer+isolate) → 6 ns; RMS offset 2 ns, skew 0.000 ppm.

4 · The warm shot

pps_prewarm.ko: an ABS_HARD CLOCK_REALTIME hrtimer fires 150 µs before each wall-clock second (the PPS rides the second boundary within ~1 µs here) and software-pends the GPIO bank-0 SPI via irq_set_irqchip_state(IRQCHIP_STATE_PENDING). The spurious interrupt walks the entire real delivery path on whichever CPU the bank targets — through the entry-stamp clock read, to an empty-GPEDS return — heating every line the real pulse needs. It cannot fabricate a PPS event (publishing is gated on the latched GPEDS bit), and GICv2 semantics guarantee exactly one activation with no re-pend (IHI0048B §3.2, Table 4-11, Fig 4-10 — the pending latch clears on IAR, not on the line).

An adversarial review (independent Grok session, two rounds) shaped the final design: round 1 was a justified NO-GO that caught a real re-arm arithmetic bug and refused to accept "a few µs of timer jitter" as folklore; round 2 accepted the rebuttal on its proposed downstream filter (our measured demux distribution made it unimplementable) in favor of the module's late-skip guard — the callback knows how late it's running and skips the poke within 30 µs of the boundary, making a warm/edge collision structurally impossible. Verdict: GO for attended A/B; production requires the watchdog (built, see §6). In service: worst observed timer lateness 8.1 µs against a 110 µs budget, zero late-skips, zero anomalies.

5 · A retraction that mattered

The "±240 ns core wobble" never existed as measured. The per-pulse analysis pipeline computed fractional seconds in float64; at epoch ~1.79×10⁹ s the ULP is exactly 238.4 ns, and MAD estimates pinned to 1.4826 × ULP = 353.5 ns — the suspiciously identical "353.5" across five windows was the analyzer, not the physics. σ values survived nearly intact (quantization added only ~69 ns in quadrature), so the era-to-era story stands, but every exact-MAD claim from the float pipeline is retracted. All of tonight's numbers come from a rewritten integer-nanosecond pipeline. Rule earned: never put an epoch timestamp through float64 and keep nanoseconds.

  • Watchdog: pps-warm-watchdog.service arms the warm shot only while chrony is PPS-locked; disarms on lock loss, skip bursts, or leaf-rate anomalies; masks bank 0 at the GIC if the leaf stalls while armed (deliberate PPS-down e-stop).
  • Mortality: a kernel version bump drops the updates/ modules. At the rpi-7.3.y rebuild, fold the steer into the carried pinctrl patch (one irq_set_affinity(girq->parents[0], cpumask_of(2)) after devm_gpiochip_add_data) and rebuild the prewarm against the new tree.

7 · The last constant, measured

With jitter solved, the remaining error was a systematic: the clock is steered so the stamp lands on the second, so it runs late by the mean delivery latency (edge at pin → entry-stamp instruction). A GPIO17→27 loopback (jumpered header pins 11→13, a second pps-gpio instance timestamping through the identical steered/warmed bank path) measured it across three duty cycles — 162,000 shots:

The phase-resolved 1 Hz data doubles as a cache-decay curve: the isolated core loses only ~38 ns of warmth across a full second — the cold cost is episodic (refresh, shared-L2 traffic), not steady decay. Net calibration: raw hot delivery ≈ 935 ns, minus MMIO write flight (≤173 ns, measured) and instrumentation adjacency → delivery latency ≈ 850 ± 90 ns, to be applied inside the QPPS daemon when it takes over steering. With cable delay compensated in the receiver, qErr corrected per-pulse, and this constant applied, every known systematic in the chain is measured out.
